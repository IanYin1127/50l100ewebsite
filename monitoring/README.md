# 成果动态与运行线索监测

系统每天检查已确认的官方栏目，将能明确匹配平台、且发布日期有效的公开条目自动展示到网站。只保存标题、链接、日期与来源，不转载正文，不自动覆盖平台名称、研究方向、联系人等基础清单。

## 首次启用

1. 合并功能 PR 到 `main`。
2. 仓库 Settings → Pages → Build and deployment → Source 选择 **GitHub Actions**。本项目原先使用分支部署，新增工作流通过 Pages artifact 发布，需切换此设置。
3. 在 Actions 中启用工作流“平台动态采集与网站发布”，点击 Run workflow 完成首次采集及发布。
4. 确认工作流的 `collect` 和 `deploy` 两个任务成功，打开网站的“成果与运行监测”，核对最近采集时间及异常来源。

任务计划为 UTC 00:17（北京时间 08:17）每天一次，GitHub 的调度可能延迟。工作流使用仓库自身的 `GITHUB_TOKEN`，无需新增付费 API 或密钥。需允许 Actions 写入仓库；如主分支保护禁止机器人推送，需要仓库维护者调整流程。推送不使用强制覆盖，发生并行修改冲突时任务会失败，避免丢失人工改动。机器人提交不会再次触发 push 工作流，本次任务会直接上传并部署生成的页面。

## 初始覆盖与限制

2026-11-05 核实了 10 个官方栏目，关联 140 / 181 条平台记录。大部分为所属高校或研究院的公共新闻栏目，只有放射医学实验室的两个栏目直接对应单个平台。**配置了来源不代表平台已被核实仍在运行，也不保证栏目会完整报道其成果。**

41 条尚未配置合适来源的记录涉及：中国科大苏州高研院、人大苏州校区、南京大学苏州研究生院／高新院、武汉大学苏州研究院、牛津大学苏州高研院、蒙纳士研究院、卡鲁研究院、洛加大研究院及梅西大学中国教育和创新中心。后续优先补充这些机构的可解析官方成果栏目或 RSS。官方主页、机构介绍或搜索结果不直接当作持续动态接口。

初始收录两条人工核实的放射医学实验室官网条目，分别为 2026-04-29 的研究成果和 2026-10-01 的科普活动；初始 `generatedAt` 为 null、已检查数量为 0，明确区分人工收录与定时任务已运行。初始状态不是伪造的实时探测结果。

采集器尊重 robots.txt；无法核实规则、403、超时、结构改变均记录为来源异常。部分官网在云环境中返回 403，必须在 GitHub Actions 首次运行后核实实际可达性。未绕过访问限制；不支持需要登录、验证码、微信公众号正文或必须执行 JavaScript 的页面。每栏目每轮最多处理 20 个不同链接，最多抓取 6 个详情页，避免高频访问；不回溯全部历史。详情预算外的条目只能依赖栏目中已有的可靠平台名称与日期，否则留待核实。高频更新的来源可单独调整预算或接入 RSS。

## 来源与平台配置

`monitoring/sources.json`：

- `sources`：已核实官方来源。记录唯一 `id`、名称、HTTPS 栏目地址、允许访问的精确域名 `allowedHosts`、`html` 或 `rss` 格式、HTML 文章 URL 正则 `articlePattern`、平台 ID、确认日期和依据，以及 `autoPublish`。
- `dedicated: true` 仅允许关联一个平台，表示已核实为该平台独立栏目；该栏目内有效日期的文章可以直接关联。普通高校／院所栏目必须在标题或限定正文区域出现完整平台名称或已核实别名。导航、页脚里的名称不用于匹配。
- `platforms`：平台 ID 使用现有数据中的“序号”，并同时保存名称和所属高校。`sourceIds` 与来源的 `platformIds` 必须双向一致。合并多名称条目的换行名称可作为别名，其他别名需核实后手动加入。
- `homepage` 只有确认是该平台的独立页面后才填写。高校或院所主页不能冒充其所有下属平台的主页。

**更新 Excel 导入的基础清单后，必须同步平台注册表。** 采集器对 ID、名称、高校执行一致性校验，防止新数据复用序号时把旧成果关联到另一个平台；页面也核对名称与高校，不展示身份不一致的动态。不能为了通过校验而机械复制旧来源和别名。

新增来源前确认机构、平台归属和栏目，填写确认依据，再开启 `autoPublish: true`。RSS 支持 RSS 2.0 和 Atom 的标题、原文链接和发布日期。不根据 HTTP Last-Modified 或抓取日期推断成果发布日期。

## 运行状态含义

- **近期有公开动态**：已收录过去 365 天的官方条目，是活动线索。
- **长期未见动态，待核实**：已有条目超过 365 天，不能据此认定停止运行。
- **来源访问异常，待核实**：该平台配置的所有来源本轮都异常。保留历史动态、连续失败次数与上次成功时间，不据此判定停运。
- **尚无匹配动态**：有来源检查成功，但尚无准确匹配的公开条目。
- **尚未执行监测／待补充官方来源**：分别表示已配栏目还未抓取、或尚未配置。
- **人工确认运行／停运**：在 `platforms[].verification` 中填写 `status: operating / ceased`、`date: YYYY-MM-DD`、`evidenceUrl`。需由维护者核验公开公告或其他可靠材料；结论有效期 180 天，过期回到自动线索状态。更名／合并应更新清单并注明依据。

页面显示最近采集时间；超过 3 天未更新会提示检查定时任务。网站可访问、栏目有更新、平台实际运行是不同事实。

## 分享、补录与纠错

网站“分享成果 / 反馈平台状态”打开 GitHub Issue 表单（需 GitHub 账号），让贡献者填写平台、高校、官方原文、日期和说明。提交不直接发布；维护者核实后编辑 `monitoring/curated.json` 的 `items`。字段包括 `platformId`、`title`、`url`、`publishedAt`、`sourceName`、`kind`（成果／动态），可记录 `discoveredAt`。标题建议简短概括，避免复制整篇原文。

自动匹配但缺少日期、日期在未来或未获自动发布授权的条目放在 `snapshot.json.pending`，不进入前端 `monitoring-data.js`。如需发布，核实后补录到 curated。误关联或需撤下的条目，将其 `id` 放入 `curated.json.rejectedIds`；下次采集会移除且不重新收录。来源临时关闭 autoPublish 只阻止后续新条目发布，不会删除历史条目。

## 本地检查

```sh
python -m unittest discover -s tests -v
python scripts/collect_updates.py --offline  # 不联网，生成人工条目与尚未监测的初始清单
python scripts/collect_updates.py            # 真实采集，保存状态与动态
node --check app.js
python -m http.server 8080
```

网站仍为原生静态 HTML/CSS/JS，采集只在维护环境／GitHub Actions 运行，Python 3.12 标准库即可，不需要网站后端。`snapshot.json` 保存完整采集状态，`monitoring-data.js` 是排除待核实条目的前端数据；手动编辑后运行脚本重新生成。
